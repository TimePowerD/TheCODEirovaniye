# Правила оформления Pull Request

При подготовке Pull Request в GitHub необходимо создавать информативное название и подробное описание на русском языке.

## 1. Название Pull Request

Используй формат:

`<тип>: <краткое описание изменений>`

Допустимые типы:
- `feat` — новая функциональность или игровая механика.
- `fix` — исправление ошибки.
- `refactor` — переработка кода без изменения поведения.
- `assets` — добавление или изменение моделей, текстур, звуков.
- `ui` — изменения интерфейса.
- `docs` — изменения документации.
- `chore` — технические изменения, настройки проекта и зависимости.

Требования:
- Название должно быть кратким, желательно до 70 символов.
- Описывай результат изменений, а не процесс разработки.
- Не используй общие формулировки вроде «Обновления», «Исправления» или «Новые файлы».
- Не перечисляй несколько несвязанных изменений, если можно выделить основное.

Примеры:
- `feat: Добавлено взаимодействие с предметами`
- `feat: Реализована система обмена объектами`
- `fix: Исправлены столкновения персонажа со стенами`
- `assets: Добавлены 3D-модели лаборатории`

## 2. Описание Pull Request

Перед составлением описания проанализируй все изменения текущей ветки относительно целевой ветки `main`.

Используй Git diff, историю коммитов и при необходимости Godot MCP для изучения изменённых сцен.

Не ограничивайся названиями коммитов. Описывай фактические изменения.

Описание должно иметь следующую структуру:

### Краткое описание
В 2–4 предложениях объясни:
- Что было реализовано или изменено.
- Для чего нужны эти изменения.
- Как они влияют на игровой процесс или структуру проекта.

### Что сделано
Подробно перечисли основные изменения:
- Новые игровые механики и их поведение.
- Изменения существующих механик.
- Добавленные или изменённые 3D-сцены.
- Изменения интерфейса, анимаций, звуков.
- Технические изменения, если они существенны.

Объясняй, как работает новая функциональность, а не просто перечисляй файлы.

### Техническая реализация
Опиши наиболее важные технические решения:
- Какие скрипты, сцены и компоненты Godot были изменены.
- Какие узлы, сигналы и взаимодействия добавлены.
- Как связаны новые компоненты.
- Какие зависимости или настройки проекта изменились.

Не перегружай описание несущественными деталями.

### Проверка работоспособности
Укажи:
- Какие проверки действительно выполнены.
- Как вручную проверить новую функциональность.
- Какие результаты получены.
- Есть ли известные ошибки или ограничения.

Не утверждай, что игра проверена или что тесты пройдены, если проверки фактически не проводились.

### Важные замечания
Если применимо, укажи:
- Незавершённые функции.
- Возможные проблемы интеграции.
- Изменения, способные повлиять на работу других участников.
- Новые сторонние ассеты и необходимость указать их лицензии в `ASSETS.md`.

Если замечаний нет, этот раздел можно пропустить.

## 3. Общие требования

1. Всё описание составляй на русском языке, сохраняя оригинальные названия файлов, методов и классов.
2. Пиши конкретно, технически грамотно и без лишней воды.
3. Описывай только изменения, которые действительно присутствуют в Pull Request.
4. Не приписывай себе работу других участников.
5. Не преувеличивай готовность функциональности.
6. Если Pull Request содержит несколько независимых изменений, логически сгруппируй их.
7. Используй Markdown: заголовки, списки и выделения.
8. Описание должно быть достаточно подробным, чтобы другой участник команды понял назначение изменений без необходимости изучать весь код.
9. При необходимости добавляй инструкции по тестированию непосредственно в Godot.
10. Не создавай Pull Request и не отправляй изменения в репозиторий без явного указания пользователя.

## 4. Итог

После анализа изменений подготовь:
1. Готовое название Pull Request.
2. Полное описание в Markdown, которое можно сразу вставить в GitHub.

Если пользователь попросил создать Pull Request и инструменты GitHub доступны, используй подготовленные название и описание при его создании.
